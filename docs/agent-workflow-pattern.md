# Agent 执行破坏性操作的流程契约

> 一份可复用的设计说明。来源于 [Windows Residual Cleaner](https://github.com/boyingliu01/windows-residual-cleaner)
> 的实战实现，但这里**刻意去掉了清理领域的细节**——留下的是任何「让 agent 执行不可逆操作」
> 的系统都需要的形状。

## 问题

让 agent 执行破坏性操作时，最常见的失败不是「模型太笨」，而是**契约缺失**：

1. agent 把「用户表达了意图」当成「用户批准了具体动作」；
2. 确认环节存在，但确认的是**计划**、执行的是**另一套目标**；
3. 出错后报告「完成」或「失败」，而真相是第三种状态（部分完成）；
4. 判断「哪些不能碰」的责任落在提示词里 —— 于是它随上下文漂移。

下面四条是解这些形状的构件。每一条都能单独拿走用。

---

## 构件 1：三道闸门，且**闸门之间目标必须一致**

确认不是一次，是三次，且每次都换一个**问题**：G1「你要处理**哪些**？」→
G2「我理解的是**这些**，对吗？」→ G3「**真的**执行吗？」。任一道被跳过，
对应的是「不得自动选 / 不得导出选择 / 不得执行」。

> 本项目这三道闸门在操作层面的落点（哪个脚手架对应哪一阶段、每道闸门的
> 具体话术与跳过后果）写在 [`SKILL.md`](../SKILL.md) 的 *Safety & Confirmation Gates*
> ——那份文档随 skill 包独立分发，是 agent 的执行手册。本节只讲**为什么是三道**，
> 不重复它的表格。

关键不在「三次」这个数字，在 **G2 的意义**：用户说「把腾讯相关的都清掉」，
agent 解析成 15 个具体条目后，必须**把 15 个条目列回去让人看一眼**。
自然语言到具体目标的翻译是幻觉最容易发生的环节，而这一步是唯一能拦住它的地方。

**反模式**：G1 之后就执行「用户已经同意了」；或者 G3 的试运行对象与正式执行对象不是同一份数据。

**实现要点**：G2 的产出必须是一个**持久化的实体**（本项目是 `confirmed-ids.json`），
后续步骤只认这个实体，不再重新解析自然语言。否则「确认过的东西」和「执行的东西」
可以不是同一批 —— 这是最隐蔽的一类越权。

---

## 构件 2：把「不可碰」做成**数据结构**，而不是提示词

最有效的安全措施不是让 agent 更谨慎，而是**让危险项在结构上无法被选中**：

```
Danger 级别 5 项已列出但不可选择清理，仅作报告。
```

注意它**仍然展示**。隐藏危险项会让用户以为「没有风险项」，展示但禁选则传达
「这里有问题，但我不会替你决定」。

- 提示词里的「请谨慎处理 Danger 项」会随上下文漂移；
- 数据结构上的「Danger 项不出现在可选集合里」不会。

**推广**：任何「agent 可能越权」的维度，都应该问「能不能把它变成类型/枚举/不可选集合」，
而不是「能不能在提示里写得更清楚」。

---

## 构件 3：诚实产物 —— 中间状态必须显式命名

失败不是二元的。每一步的结果都必须编码成**互斥的命名结果**，而不是一个布尔值：

| 结果 | 含义 |
|------|------|
| 真的没了 | 与「还在」必须能分辨 |
| **还在磁盘上，只是换了名字** | 语义上**不是**成功 |
| 本来就没有 | 幂等，不是失败 |
| 只是试运行 | 没动过任何东西 |
| 没做到 | 失败 |

`renamed` 这一态是核心：底层的最后兜底是**改名**而不是删除（内容仍在，靠重启清理）。
如果报告把它折叠进「成功」，就是在教用户相信一件不真的事。本项目的四层降级
里哪一层产出哪一态，见 [`SKILL.md`](../SKILL.md) 的 *What "deleted" actually means*。

**判据**：如果某个操作有多条实现路径，那么**每条路径的语义差异必须出现在返回类型里**，
而不是出现在日志里。调用方只看得到返回值。

**推广**：给不出精确措辞时，宁可返回 `unknown` 并让人看一眼，也不要返回一个乐观的猜测。
本项目的退出码映射表在遇到不认识的 outcome 时**落到 14（交回人工）而不是 0** ——
一张没更新过的映射表不该有权宣告成功。

---

## 构件 4：「失败之后」是一等公民

大多数系统只设计成功路径。破坏性操作必须把**回滚**当成主路径的一部分：

1. **先记账再动手**：变更前写日志（journal），失败则本轮不该开始；
2. **自动回滚**：部分失败时自动撤销已做的变更；
3. **退出码承载回滚状态**：不是「成功/失败」，是「失败且已回滚/失败且未回滚干净/无法判断/未开始」；
4. **回滚本身也会失败**：所以回滚状态必须能被单独读出，且当它不确定时**不得**写「本轮已完成」标记
   —— 否则下一轮永远不会再尝试恢复。

本项目的编码（可供直接借用）：

<!-- BEGIN GENERATED: exit-codes -->
| 码 | 含义 |
|----|------|
| 2 | Permission denied (not elevated) — deletion needs Administrator. |
| 1 | Required input JSON missing — run the scan first. / 部分失败但本轮没有任何已变更记录（REQ-020「未执行到回滚即失败」） |
| 3 | Required input JSON missing — run the scan first. |
| 14 | **上一轮**未安全消费，本轮**未开始** |
| 15 | 记账写入失败（状态未知） |
| 13 | 部分失败且 -NoAutoRollback |
| 12 | 部分失败但回滚日志缺失/不可读 |
| 11 | 部分失败且回滚未完全成功（存在 restore_failed） |
| 10 | 部分失败且回滚完全成功 |
| 0 | 没有失败 |
<!-- END GENERATED: exit-codes -->

两个容易被忽略的设计点：

- **`14` 与 `15` 不是「操作失败」**，是「记账完整性」问题。混为一谈会让用户去修错的东西。
- **完成标记的抑制判据**只有一个问题：*系统此刻是否仍有本轮没能修复的改动*。
  只要答案是「是」，就不许写完成标记。这条比任何「失败时记得…」的清单都可靠。

## 构件 5（补充）：**危险面必须随组件一起声明**

如果系统有一个便利入口（本项目：一个本地 HTTP 服务，会拉起管理员权限的破坏性脚本），
那么它的风险必须在**该入口出现的地方**被写明，而不是只在安全文档里。

判据：**读者会照着他看到的那一页去启用它。** 只要那一页没写「这个会以管理员权限执行删除」，
就等于没写。

---

## 配套的「不要暴露」清单

反过来，也要显式列出**不应该**抛给用户的实现细节（参数名、文件名、模式代号）。
本项目的做法是在文档里单独一节「What User Never Needs to Know」，
并给出唯一例外：

> 退出码里表示「改动仍在生效」或「状态未知」的那几个，**是发现，不是实现细节**。
> 必须翻译成自然语言并一定传达。

这条区分的价值在于：它防止 agent 用「不打扰用户」当借口，把危险信息也一起藏掉。

## 自检清单

拿去用在别的场景时，逐条问：

- [ ] G1/G2/G3 三道闸门是否都存在？G2 的产出是否是持久化实体？
- [ ] 正式执行读的目标，是否**就是**用户确认过的那一份？
- [ ] 有没有哪个「不该做」的判断，其实还可以挪进数据结构？
- [ ] 每种中间状态（尤其「做了但没完全做到」）是否有独立名字，且**不被计入成功**？
- [ ] 回滚状态是否出现在返回类型里，而不只是日志里？
- [ ] 回滚本身失败时，有没有阻止「本轮已完成」被写下？
- [ ] 不认识的输入，是落到保守态还是乐观态？
- [ ] 每个便利入口的风险，是否写在读者会看到的地方？
- [ ] 「不要暴露」清单里，是否明确排除了危险信息？
